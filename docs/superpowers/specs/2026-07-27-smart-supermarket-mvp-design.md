# 鲁能超市李老家分店智慧超市系统 MVP 设计规格

- 文档日期：2026-07-27
- 设计状态：已完成讨论，等待书面规格审阅
- 原始依据：《鲁能超市李老家分店智慧超市系统项目规划书 V1.0》

## 1. 项目目标

第一阶段建设一套可在鲁能超市李老家分店小范围真实试运营的智慧超市 MVP，先验证“顾客线上选购并提交订单，门店确认备货，顾客到店付款取货”的最小业务闭环。

MVP 的成功标准不是完整覆盖规划书中的所有能力，而是让真实商品、顾客、员工和订单能够稳定运行，并为后续配送、称重、预定、会员营销和扫码收银保留清晰的扩展边界。

## 2. 已确认的 MVP 范围

### 2.1 顾客侧

- 使用微信原生小程序。
- 浏览首页、商品分类和商品列表。
- 搜索商品并查看商品详情。
- 将普通定量商品加入购物车并修改数量。
- 使用微信登录。
- 首次下单时填写取货人姓名和手机号。
- 提交到店自取订单。
- 查看自己的订单列表、详情和处理状态。
- 在门店接单前主动取消订单。
- 在小程序内查看备货结果；必要时由门店电话联系。

### 2.2 门店侧

老板和收银员共用一套 Vue 3 管理后台，但使用独立账号和不同权限。

老板可以：

- 管理商品分类。
- 新增、修改、上下架商品。
- 上传和管理商品图片。
- 设置及调整线上可售库存。
- 查看、确认、拒绝和处理订单。
- 标记备货完成、线下已付款、订单完成或取消。
- 创建、停用和重置收银员账号。
- 查看关键操作记录。

收银员可以：

- 查看订单。
- 接单或拒单。
- 更新备货状态。
- 确认线下付款。
- 完成或取消订单。

收银员不能管理商品、库存、员工账号和系统设置。

### 2.3 商品、履约与付款

- MVP 只支持普通定量商品。
- 不建设复杂 SKU 体系；不同包装或规格作为独立商品管理。
- 履约方式只支持到店自取。
- 顾客到店后使用现金或门店微信收款码付款。
- 老板或收银员在后台手动确认付款。
- 线上使用独立可售库存，不与尚未接入系统的线下收银库存自动同步。

### 2.4 明确排除的功能

以下功能不进入 MVP：

- 配送到家。
- 微信在线支付。
- 积分、会员等级、会员余额和优惠券。
- 称重商品和电子秤对接。
- 预定商品、定金和尾款。
- 扫码购物、扫码收银和电子小票。
- 微信订阅消息和短信通知。
- 秒杀、满减及节日营销。
- 销售分析、智能推荐和自动补货。
- 独立员工操作端。

## 3. 技术路线

采用规划书指定的技术栈：

- 顾客端：微信原生小程序 + TDesign MiniProgram，图标统一使用 TDesign Icons。
- 管理后台：Vue 3 + Element Plus。
- 后端：Java 17 + Spring Boot 3。
- 数据库：MySQL 8。
- 缓存及短期状态：Redis。

前端组件库边界：

- 小程序不得混用 Vant Weapp、WeUI 等其他完整组件库。
- 小程序的按钮、搜索框、标签、弹窗、Toast、骨架屏、步进器、标签页与底部导航优先使用 TDesign MiniProgram。
- 首页业务卡片、商品卡片、分类入口和推荐专区按项目视觉规范自定义，禁止直接套用组件库零售模板的默认视觉。
- 管理后台统一使用 Element Plus，不再引入第二套完整后台组件库。
- 两端主题变量均映射至已确认的“深绛红”视觉系统。
- 认证与授权：JWT。

## 4. 总体架构

项目采用“模块化单体 + 单仓库”架构。仓库按以下顶层目录组织：

- `mini`：顾客微信小程序。
- `admin`：老板与收银员共用的管理后台。
- `server`：Spring Boot 模块化单体后端。
- `database`：数据库初始化、迁移和测试数据。
- `docs`：需求、设计、接口与部署文档。

后端作为一个可独立部署的应用，内部按业务职责划分为：

- 认证与用户。
- 商品与分类。
- 线上库存。
- 购物车下单校验。
- 订单。
- 后台权限。
- 操作审计。
- 文件访问。

MySQL 是用户、商品、库存和订单等核心数据的唯一事实来源。Redis 只保存缓存、可撤销的短期登录状态、防重复提交标识及其他可重建数据，不保存不可丢失的核心业务数据。

小程序 MVP 只接入微信登录，不接入微信支付、微信订阅消息或短信平台。

## 5. 模块职责与边界

### 5.1 认证与用户

- 使用小程序登录凭证换取微信顾客身份。
- 为顾客签发系统访问令牌。
- 保存顾客基础资料和默认取货信息。
- 管理后台员工账号、登录状态和角色。
- 强制执行老板、收银员和顾客的权限边界。

### 5.2 商品与分类

- 管理分类名称、排序和启用状态。
- 管理商品名称、分类、售价、单位、封面图、详情和上下架状态。
- 向小程序提供可售商品的浏览、搜索和详情接口。
- 商品上下架或价格变化不修改历史订单内容。

### 5.3 购物车

- 购物车保存在小程序本地。
- 顾客可以在未登录状态下浏览和维护购物车。
- 提交订单前必须完成微信登录和取货信息填写。
- 后端不信任客户端金额，提交时重新校验商品、价格和库存。

### 5.4 线上库存

- 每个商品维护独立线上可售数量。
- 所有变动生成库存流水。
- 库存流水记录变动数量、变动前后数量、原因、关联订单、操作人和时间。
- 通过事务和并发控制防止线上超卖。

### 5.5 订单

- 创建订单并保存商品及价格快照。
- 维护订单状态、付款状态和状态历史。
- 校验每一次状态转换是否合法。
- 处理取消订单后的库存返还。
- 确保重复请求不会重复创建订单或重复返还库存。

### 5.6 后台权限与审计

- 后端根据角色校验每个管理接口。
- 前端菜单和按钮根据权限展示，但不能替代后端权限判断。
- 记录商品、库存、订单和员工账号的重要操作。

### 5.7 商品图片

- MVP 将商品图片保存在服务器的专用文件目录。
- 数据库只保存图片访问地址。
- 上传时限制文件类型、大小和访问路径。
- 图片目录与数据库一起纳入定期备份。

## 6. 核心数据模型

### 6.1 顾客

保存微信 `openid`、昵称、头像、默认姓名、手机号、启用状态及时间信息。顾客只能访问自己的订单。

### 6.2 员工账号

保存用户名、密码安全哈希、角色、启用状态、最后登录时间及时间信息。MVP 角色为老板和收银员。

### 6.3 商品分类

保存名称、排序、启用状态及时间信息。

### 6.4 商品

保存名称、分类、售价、单位、封面图、详情、上下架状态及时间信息。价格统一使用人民币“分”为单位存储和计算。

### 6.5 线上库存

保存商品、可售数量和并发控制版本。库存不能小于零。

### 6.6 库存流水

保存变动数量、变动前后库存、变动原因、关联订单、操作人及时间。流水用于核对库存，但当前库存仍以线上库存记录为准。

### 6.7 订单

保存订单号、顾客、取货人姓名、手机号、订单总金额、订单状态、付款状态、取消方、取消原因及各业务时间。

### 6.8 订单明细

保存订单、商品标识、商品名称快照、单位快照、单价、数量和小计。

### 6.9 订单状态记录

保存每一次状态变化的原状态、新状态、操作人、备注和时间。

### 6.10 后台操作日志

保存操作账号、操作类型、业务对象、结果摘要、请求标识和时间。日志避免记录密码、令牌等敏感值。

## 7. 订单、付款与库存状态

### 7.1 订单主流程

正常状态流转为：

`待门店确认 → 备货中 → 待取货 → 已完成`

异常结束状态统一为“已取消”，同时记录取消方和取消原因。

### 7.2 创建订单

顾客提交订单时，后端在同一数据库事务内：

1. 校验顾客身份和取货信息。
2. 校验所有商品均已上架。
3. 读取后端当前价格并计算订单金额。
4. 原子检查并扣减所有商品的线上可售库存。
5. 创建订单、订单明细、状态记录和库存流水。

任一商品无效或库存不足时，整个事务失败，不创建部分订单，也不扣减部分库存。

### 7.3 接单与备货

- 新订单进入“待门店确认”。
- 顾客可以在该状态自行取消。
- 老板或收银员确认有货后，将订单变为“备货中”。
- 门店无法履约时，可以取消订单并填写原因。
- 备货完成后，门店将订单变为“待取货”。

门店接单后，顾客不能在小程序直接取消，需要联系门店，由老板或收银员处理。

### 7.4 付款与完成

- 付款状态独立保存为“未付款”或“已付款”。
- 顾客到店后使用现金或门店微信收款码付款。
- 老板或收银员手动将订单标记为“已付款”。
- 只有已付款且处于“待取货”的订单才能变为“已完成”。

### 7.5 取消与库存返还

- 未完成订单可由有权限的一方按规则取消。
- 取消操作记录取消方、原因和时间。
- 取消订单与返还库存必须在同一事务中完成。
- 同一订单只能成功返还一次库存。
- 已完成订单不能直接取消；MVP 不包含退款或售后流程。

## 8. 安全设计

- 所有生产接口使用 HTTPS。
- 小程序登录凭证仅由后端与微信服务交换。
- 顾客和员工使用逻辑隔离的认证入口与权限规则。
- 员工密码只保存安全哈希。
- 后端对所有受保护接口执行身份、角色和数据归属校验。
- Redis 保存可撤销的短期登录状态，支持账号停用后令牌失效。
- 登录、下单等敏感接口实施频率限制。
- JWT 密钥、数据库密码和微信配置通过部署环境注入，不提交到仓库。
- 手机号等个人信息只在业务需要的页面展示。
- 日志和错误响应不包含密码、令牌或完整敏感配置。

## 9. 异常处理与一致性

- 下单接口使用一次性请求标识，防止重复点击生成多张订单。
- 商品下架、价格变化或库存不足时，后端拒绝下单并返回需要处理的商品。
- 所有订单状态变更校验当前状态，拒绝非法或重复转换。
- 核心写操作使用数据库事务，失败时整体回滚。
- 客户端网络中断后重新查询订单结果，不盲目重复提交。
- 后端统一业务错误结构，向用户返回可理解的提示，同时记录可检索的错误编号。
- 库存、订单、商品和账号操作保留审计信息。

## 10. 测试策略

### 10.1 后端测试

- 单元测试覆盖价格计算、库存扣减与返还、订单状态转换和权限判断。
- 数据库集成测试覆盖事务回滚、并发下单和防重复提交。
- 接口测试覆盖认证失败、权限拒绝、参数错误和业务异常。

### 10.2 小程序测试

- 覆盖微信登录、商品浏览、搜索、购物车、下单、取消及订单查询。
- 覆盖商品下架、价格变化、库存不足和网络重试提示。

### 10.3 管理后台测试

- 覆盖老板与收银员的菜单、操作权限和后端接口权限。
- 覆盖接单、拒单、备货完成、确认付款、完成及取消流程。
- 覆盖商品、库存和员工管理。

### 10.4 端到端与并发测试

- 完整跑通顾客提交至门店完成的正常流程。
- 验证顾客取消和门店取消后的库存恢复。
- 验证多人同时购买同一低库存商品时不会超卖。
- 验证重复提交、重复取消和重复确认不会产生重复数据。

## 11. 部署与运维

试运营环境包含：

- 一套 Spring Boot 后端服务。
- 一套管理后台静态站点。
- MySQL 8。
- Redis。
- 商品图片专用目录。
- HTTPS 入口和访问日志。

部署环境必须配置小程序所需的微信身份信息和可访问的 HTTPS API 地址。测试环境与试运营环境使用独立配置和数据。

数据库和商品图片执行定期备份。上线前至少进行一次恢复演练，确认备份可以用于恢复。应用保留基础运行日志和业务错误编号，以支持试运营问题排查。

## 12. MVP 验收标准

试运营验收至少满足：

- 录入不少于 30 个真实商品及对应线上库存。
- 创建 1 个老板账号和不少于 1 个收银员账号。
- 不少于 5 位顾客完成微信登录。
- 完整跑通不少于 10 笔真实或试运营订单。
- 订单金额、付款状态和库存流水保持一致。
- 老板与收银员权限隔离正确。
- 同一商品并发下单不会导致库存小于零。
- 取消订单不会重复返还库存。
- 核心业务流程不存在阻断试运营的严重问题。

## 13. 后续扩展方向

MVP 验证通过后，后续能力按独立设计、实施和验收周期逐步加入：

1. 配送范围、配送费、地址和配送订单。
2. 微信在线支付及支付回调。
3. 会员积分、等级、余额和优惠券。
4. 称重商品、标签和电子秤对接。
5. 春节预定、定金、尾款和取货通知。
6. 扫码购物、扫码收银和电子小票。
7. 销售分析、库存预警和智能运营。
